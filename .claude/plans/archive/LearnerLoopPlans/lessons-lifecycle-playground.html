Step 1 · Orientation

Each earnings event runs a 4-phase loop

A "lesson" is the unit of memory the system carries forward. Before we look inside, here's the shape of the whole cycle.

A
Build
7 builders fetch data; the orchestrator stitches a context bundle. Lessons from prior quarters are pulled in.
B
Predict
A forked Claude skill reads the bundle and emits a directional call PLUS a label for every prior lesson it saw.
C
Learn
After the 8-K event horizon, an embedded Claude session gets the actual return and explains why the stock moved.
D
Mutate
Python writes the new lesson to the library AND audits the prior lessons against the realized outcome.
The fundamental asymmetry
Predictor
forked SDK skill — fresh context, no shared memory. Bundle is its only input.
Learner
SDK embed in main session — full Data SubAgent access. Writes one JSON. Python handles aggregation.
Predictor PIT
Q_n.filed_8k — must be blind to anything after release.
Learner PIT
Q_{n+1}.filed_8k — deliberately later. The intent is that lessons typically aren't written until the next cycle's data arrives, with fallback tiers (live cycle, then invocation time) when no next quarter exists in the events list.

Why each field exists

lesson
The heuristic itself. The future predictor copies this verbatim into lesson_text. ≥30 chars.
mechanism
The causal chain. Names which segment of the market reprices what, and why. ≥30 chars. The non-negotiable bar — without it, you have a slogan.
applies_when
The bundle preconditions. Future predictor uses this to choose confirmed vs irrelevant. ≥30 chars.
invalid_if
Conditions that nullify or invert the lesson. Forces the learner to name failure modes. ≥30 chars.
evidence_refs
Ledger IDs from THIS quarter that DIRECTLY demonstrate the mechanism. Non-empty. Tangential refs are an explicit reject signal.
The 8 invalid-lesson signals (auto-reject by the rubric)
  • Only describes price patterns or peer movement without explaining transmission
  • Generic phrases ("sell the news", "buy the dip", "stocks like this go down")
  • Applies equally to any company / sector / regime (tautology)
  • Embeds thresholds disconnected from mechanism (numbers without causal WHY)
  • Memorizes prior outcomes (recall without mechanism)
  • Mechanism longer than the lesson body (fluff inflation)
  • Vague actors ("investors", "the market") without naming WHICH segment
  • evidence_refs that don't directly prove the mechanism (tangential)

What the persistence layer adds on top of the 5 content fields

When append_ticker_lesson / append_global_lessons stamp a lesson into the library, it gains:

  • lesson_id — content-addressed sha256[:10] hash orchestrator
  • scope + routing_key — derived from emission context
  • audit_history: [] — populated only by future aggregate_lesson_audits runs
  • parent_id — null on births; set only when this lesson is a refinement
  • Plus provenance for global-scope lessons: source_ticker, source_sector, quarter_label, attributed_at, source_filed_8k, source_pit_cutoff + the scope-conditional routing field at top level (target_sector for sector, related_tickers for cross_ticker)

So the persisted record is a 10-field (ticker) or 16+ field (global) dict, even though the learner only writes 5.

Step 3 · Identity

Every lesson has a content-addressed ID

Same body + scope + routing → same id. This is what makes re-emission idempotent and makes refinements distinguishable from cosmetic edits.

lesson_id = "lsn_" + sha256(
    normalized_body + "|" + scope + "|" + routing_repr
)[:10]

normalized_body = " ".join(body.strip().split()).lower()

The 4 scopes (and what their routing_key looks like)

scopewhere it livesrouting_keyexample
ticker learnings/ticker/{T}.json uppercase ticker symbol "FCX"
sector learnings/global.json canonical sector string "BasicMaterials"
macro learnings/global.json None —
cross_ticker learnings/global.json sorted tuple of UPPERCASE tickers ("FCX","NEM","SCCO")

Three guarantees this gives you

  • Idempotent re-emission. Re-running on the same audit → no duplicate lessons.
  • Refinement is detectable. A reworded body → different hash → different lesson_id (parent_id chain).
  • Cross-scope same-text gets different ids. A sector-level lesson and a ticker-level lesson with the same body do NOT collide — scope is in the hash.
The D22 collision check

Before any write, Python scans the target library for the lesson_id. If found AND content differs → DuplicateLessonIdError (loud halt). If found AND content matches → no-op (legitimate idempotent re-emit).

Keyspace: 16^10 ≈ 1.1×10¹². Birthday collision probability ≈ 10⁻⁴ at 10⁴ lessons.

Step 5 · Birth

A lesson is born by the learner, never the predictor

The learner runs after the 8-K event horizon, with the realized return. Lessons emit in three buckets: ticker-scope (predictor_lessons), global-scope (global_observations), and operational (data_lessons).

The three emission buckets

predictor_lessons
Up to 3 per learner run. Ticker scope. Routes to ticker/{T}.json only.
global_observations
Up to 3 per learner run. Sector / macro / cross_ticker. Routes to global.json.
data_lessons
Up to 3, list of strings. Operational instructions ("fetch X", "weight X more"). Not a market hypothesis — different shape on purpose.
The "default narrower" rule

If you can defend it as ticker-scope, do that — don't promote it to sector. Asymmetry favors narrower-when-uncertain because over-broadening misleads peer predictions; under-routing only hurts coverage.

Step 6 · Read

To reach the predictor, a lesson runs a 6-stage gauntlet

Library has thousands of lessons, but the predictor sees only a curated subset shaped by point-in-time, scope, status, and caps.

1
Load + dedupe Read library files. Sort by attributed_at desc. Dedupe ticker rows by quarter_label (keep most recent — covers re-bootstrap).
2
PIT filter (T1.5b) Keep only lessons where source_pit_cutoff ≤ predictor.pit_cutoff. Live mode (cutoff=null) bypasses. Naive datetimes rejected.
3
Same-quarter self-leak guard (D13) Drop any lesson whose (source_ticker, quarter_label) equals THIS quarter. Prevents the predictor from "remembering" its own future.
4
Render view per lesson Filter audit_history by audit_pit_cutoff. Compute status. Drop retired. Attach transient _render_status + _render_audit_counts.
5
Scope routing (globals) sector → must match current ticker's sector. cross_ticker → current ticker must be in related_tickers. macro → always passes. 6 named exclusion counters log every drop.
6
Caps Ticker rows ≤ 8. Sector ≤ 4. Macro ≤ 4. Cross-ticker ≤ 2. Cap-binding telemetry logs eligible vs rendered counts so you know when caps actually drop signal.

Step 10 · Evolution

Lesson state evolves from audits

A pure function over the lesson dict — compute_status() — runs at bundle-build time. No cron job, no batch job. The state is always recomputed from the audit history.

The pure-function rules (in evaluation order)

  1. Filter audit_history to those with audit_pit_cutoff ≤ predictor.pit_cutoff.
  2. If ANY visible audit has action ∈ {retire, refine} → retired. (Terminal.)
  3. Take the last 5 visible audits. Count review == "misled".
  4. If misled-count ≥ 3 → retired.
  5. If misled-count ≥ 2 → watch.
  6. Otherwise → active.

Crucially: what does NOT cause penalty

  • missed — predictor underuse is not lesson weakness. Penalizing it would damage good lessons whose triggers the predictor failed to recognize.
  • outweighed — the lesson's reasoning was sound; other forces dominated. The lesson stays in good standing.
  • neutral — predictor's call was correct.
  • unclear — hindsight insufficient.

Step 12 · Time

Two PITs, deliberately different

The predictor must be blind to anything after the 8-K release. The learner must NOT see anything until the next quarter's data arrives. These are different cutoffs — by design, not by accident.

The 3-tier learner PIT derivation

  1. Tier 1. If Q_{n+1} exists → use Q_{n+1}.filed_8k. (Almost always.)
  2. Tier 2. No Q_{n+1} but a live cycle in live_state.json → use that filed_8k.
  3. Tier 3. No live cycle either → datetime.now() at invocation time.

Stamped on each lesson as source_pit_cutoff. Stamped on each audit as audit_pit_cutoff.

Why the asymmetry matters for learning

If the learner's cutoff equaled the predictor's, the learner would have to attribute moves with the same data the predictor saw — i.e., it couldn't observe what actually moved the stock. By trailing one quarter, the learner sees the next earnings cycle's read on the prior event AND has time for analyst revisions, transcripts, follow-up filings.

If you're rebuilding from scratch — what quality bar should the audit pipeline enforce so this can't happen? Should a learner run that doesn't write its full artifact tree be allowed to mutate library state at all?
  • Missing signals. The system can't distinguish "lesson is too narrow / never fires" from "lesson is correctly scoped / fires when applicable" — both look identical at this stage: empty audit_history or [neutral, neutral, …].

What "smarter" means in this system

  • Lessons accumulate evidence over quarters. Each audit is a data point.
  • Bad lessons get squelched. Misled signal compounds. After enough hits, the lesson stops rendering.
  • Refinements re-enter at full strength. A refined child has empty audit_history — it gets a clean shot.
  • The predictor's read of a lesson is audit-aware. A tag like [reviews: 1 neutral] or [reviews: 2 helped, 1 misled] surfaces alongside the body so the predictor can weight accordingly.
What this system does NOT do (potential design gaps to critique)
  • Doesn't promote lessons that have N "helped" reviews — there's no reward state, only a punish state.
  • Doesn't track inter-lesson interactions — no notion of "this lesson + that lesson together helped/misled".
  • Doesn't measure base rate — a lesson that fires often vs rarely both compete on the same window=5 threshold.
  • Doesn't share state across tickers for ticker-scope lessons — a lesson FCX learned can't help NEM unless promoted to sector.
  • Doesn't have "near-miss" detection — a lesson that almost applied gets no signal.

Step 14 · Proposal

Lessons must earn visibility, not inherit it

Steps 1-13 described what the system does today. The remaining steps propose a tightening that improves learning quality inside the current architecture — no rewrite, no new storage.

A lesson should not become powerful because it exists. It becomes powerful only when audit history proves it helped or was missed.

Now

Predict → Learn → Store → Render by recency / status

Status only knows three values: active / watch / retired. Inside "active", a lesson with [helped, helped, helped] ranks identically to one with [neutral, neutral]. Recency wins.

→

After

Predict → Learn → Audit → Score → Tier → Rank → Render with trust level

Tier derived purely from audit_history. Rendered with the trust level visible to the predictor. Cap allocation fills high-trust tiers first.

Reality check against the FCX corpus

(Stale-neutral kicks in only after ≥2 neutral-only audits accumulate.) Q3's neutral audits prove correct non-application — they do not prove predictive value. So the lessons should remain visible but should NOT raise predictor confidence on their own.

What changes minimally — and what stays
  • Stays: entire predictor / learner / aggregator pipeline. Same 5-field lesson schema. Same review/action enums. Same PIT discipline. Same library files.
  • Adds: a transient _render_tier field attached in _apply_render_view alongside the existing _render_status and _render_audit_counts.
  • Changes: sort comparator goes from attributed_at desc to (tier_priority, attributed_at desc). Caps still apply per-scope; tier just orders within the cap.

Caveat I want to flag: tier should NOT mechanically raise predictor confidence. The predictor remains skill-instructed — a tier-promoted lesson means "consider weighting this more if conditions are met", not "auto-bump score". Mechanical confidence-bumps would let a small number of overfit lessons compound errors.

Step 24 · Minimal v0

The novice applicability test

A person who has read ONLY the bundle (no market intuition, no domain priors) must reach the same applicability verdict as the production system. If they can't, the lesson isn't reusable — it's intuition wearing a lesson costume.

Lessons that depend on bundle-undetectable qualitative judgment:

Step 26 · Minimal v0

Brier score = the primary prediction-quality metric

Mean squared error between predicted probability and actual outcome. Lower is better. It rewards honest calibration, not just being right.

Why Brier and not just accuracy:

A 60%-accurate predictor whose "70% confident" calls actually win 70% of the time beats a 65%-accurate predictor whose "70% confident" calls win 50% of the time. The first is tradable. The second isn't.

Five guardrails (must not regress)

  • Directional accuracy (don't sacrifice direction for calibration)
  • no_call precision (when we skip, we should be right to skip)
  • Citation precision (cited lessons must actually help)
  • Rolling-window trend (last 50 ≥ prior 50)
  • Bounded blast radius (no single lesson causes most misleds)
