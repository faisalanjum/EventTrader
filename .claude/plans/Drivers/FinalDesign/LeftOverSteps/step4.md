# Step 4 — Build the one Driver reuse-and-creation decision system

## Plain goal

For every fact produced by Step 3, decide safely:

* reuse this exact existing Driver;
* reuse it after a harmless word-order correction;
* create a new Driver;
* skip an unusable candidate; or
* park it only until an exact registered trigger can change the result.

A Driver is the reusable cause or standing measure. This step decides its identity. A wrong reuse is worse than creating a temporary duplicate, so uncertainty always stays separate or stops.

Fact proposed by the shared reader
↓
Find possible existing Drivers
↓
Same meaning? ── yes → reuse
│
no or unsure
↓
Lawful and clear? ── yes → create separately
│
no
↓
Skip or exact-trigger park

## Important current state

* accepts recorded decisions only;

Step 4 must reuse that proven planning seam where appropriate, then connect the real decision system to the V2 event path. It must not create a parallel writer or event route.

## The decision flow

### Stage 0 — Mechanical intake

Code performs only exact mechanical checks:

1. Validate the proposed name through the existing name-format owner.

2. Normalize typography only through the existing normalizer:

   * case;
   * Unicode representation;
   * separators;
   * whitespace.

3. Never stem, singularize, expand acronyms, or infer synonyms.

4. Apply only the officially frozen banned-token rule from its single owner.

5. Detect exactly one terminal _guidance or _surprise suffix through the existing suffix owner.

6. Check the proposed per-unit denominator against the written-out name:

   * use Step 3’s per_x value;
   * compare through the official name structure;
   * no acronym list, unit-text scan, substring shortcut, or special case;
   * uncertain expansion must already have been skipped by the reader;
   * any name-to-denominator conflict parks.

7. Check exact-name collisions across:

   * stored Drivers;
   * reversible same-meaning variants;
   * permitted empty base anchors;
   * protected offline cards.

8. Retrieve only Drivers visible at the event’s publication time.

9. Build the bounded reuse display.

A proposal remains temporary here. It must not determine a stored ID or permanent fact type.

### The bounded reuse display

For each proposal, show only:

* the exact normalized-name match first, when present;
* at most the officially frozen number of semantic suggestions;
* Driver name;
* permanent fact type;
* young, established, frozen, or quarantined state;
* base-metric relationship;
* reversible same-meaning variants;
* at most two evidence quotes public by the event time.

Never show:

* future evidence;
* full stored facts or values;
* structured-filing concepts;
* hidden empty base anchors;
* parked or quarantined targets;
* similarity scores;
* company counts, industry counts, or mention counts;
* the full catalog;
* model reasoning.

Search every Driver visible at the event time; never restrict candidates to the
same company or industry. The source and candidate industry labels may be shown
as context. Semantic search may suggest and order candidates only; it never
authorizes reuse. Production prompts and code must contain no named
industry-pair example.

### Stage 1 — Meaning decision

Use one bounded identity-judge request per event, following the exact Step 2
role assignment. The request is independent of the reader and router and must
return one action for every proposal. It may batch the event's proposals; do
not create one call per proposal. Exact replay of an unchanged frozen decision
reuses that decision and is not a new model call.

For each proposal, return one approved action:

#### ATTACH

Reuse an exact-name Driver only when its evidence confirms:

1. the same cause or object;
2. the same business scope;
3. the same mechanism.

An exact spelling is never sufficient by itself.

Additional rules:

* A quarantined Driver cannot receive new facts.
* A suspected homonym must be re-coined more specifically once; if no safe name exists, skip it.
* Every exact-name match requires the Sonnet 5 high-effort identity judge.
* A refusal can never be overturned into acceptance by a weaker model.
* An unresolved meaning keeps the Drivers separate or skips the candidate. A
  timeout fails closed and is retryable only if Step 10 derives an exact
  authorized service-state trigger.

#### ADOPT

Use an existing Driver after a harmless token-order change only when:

* the model confirms the same cause, scope, and mechanism;
* code proves the two names contain exactly the same token multiset;
* no token was added, removed, stemmed, expanded, or replaced.

After verification, treat it as ATTACH. Do not create a permanent alias merely for word order.

#### Different wording, possibly same meaning

The router may propose a possible same-meaning pair, but it never decides the link.

The synchronous link remains off. Therefore:

* create the lawful candidate under its own wording;
* send the pair to a later invocation of the same identity judge;
* keep both histories separate meanwhile;
* never move or re-key a fact later.

If the target is quarantined or otherwise flagged, park the candidate only on
the existing exact quarantine-clear or recovery trigger instead of creating
duplicate Drivers around a possibly corrupted target.

#### CREATE

Create separately only when:

* no safe existing match survives;
* the name is lawful, specific, reusable, and source-grounded;
* permanent fact type can be safely stamped;
* required family relationships can be resolved;
* at least one fact survives all existing validation.

#### SKIP

Skip when the proposal is:

* vague;
* not reusable;
* only a one-time source description;
* based on an uncertain per-unit expansion;
* impossible to name safely.

A skip is counted and source-linked. It never silently disappears.

#### PARK

Park only when the owning rule exposes all of:

* one typed reason;
* one exact machine-observable state or evidence trigger that can change the
  result;
* the whole event to reconsider;
* the evidence that remains bound to that original event.

A temporary gate, missing base, incomplete source state, or quarantine may park
only when its existing owner supplies that exact trigger. Vague meaning,
conflicting permanent type, a rejected rule, a rejected identity decision, or
mere passage of time is terminal: skip, reject, or keep separate. A later
source is processed as its own event and fact. It may trigger reconsideration
of an older whole event only through an owner-proved relationship or state
change, and the older event may not borrow its quote, value, unit, period, or
meaning.

Do not accept facts merely to reduce park rates.

### Uncertainty rule

* Unsure whether two lawful names are the same: keep them separate.
* Unsure whether the candidate itself is lawful or correctly typed: park only
  on an exact registered trigger; otherwise skip or reject.
* Never use a model confidence score as permission.
* Do not add a separate UNSURE mechanism unless Step 2 explicitly enabled it.

## Finalizing the proposal

The Step 3 fact is still a proposal until this point.

The lifecycle must be:

Reader proposal
→ identity decision
→ final Driver name and permanent fact type
→ fresh immutable finalized fact
→ existing period/unit/slice/ID/validation path

Requirements:

* Never mutate a proposed fact in place.
* Never build a stored fact ID from the proposed name.
* Create the final immutable fact through the existing construction owner.
* A stored Driver’s permanent type wins on reuse.
* A permanent type mismatch refuses reuse. Keep a lawful distinct candidate
  separate or reject it; never silently correct or blindly retry it.
* A newly created Driver receives its permanent type only after the required checks pass.
* The final decision and its evidence must be included in the existing run audit.
* Model explanations are evidence records, never executable instructions.

## Permanent type and family rules

Build one stamp_fact_type owner and one resolve_base_metric owner shared by live admission and offline catalog finalization.

### Terminal guidance and surprise names

For a name ending in _guidance or _surprise:

* strip exactly one terminal suffix;
* stacked suffixes reject;
* mid-name words do not count;
* run the exact approved semantic question twice independently;
* both answers must be yes and cite the evidence;
* disagreement, unclear evidence, or failure blocks creation;
* freeze the decision memo; never rerun it on refresh;
* create exactly one BASE_METRIC relationship to a proven metric;
* if no real base exists, the only lawful empty node is the exact permitted base anchor;
* never fuzzy-match or approximately graduate that anchor.

### Bare names

Apply the frozen order:

1. deterministic terminal and approved bare-root rules;
2. exact locked fact-type classifier;
3. if it says action, stamp action;
4. if it says guidance or surprise on a bare name, re-coin with the required suffix or skip;
5. if it says metric, run the metric-proof challenge;
6. in live thin evidence, unclear means skip unless an existing owner exposes
   an exact trigger that can change the result—never default;
7. permanent type is written once and never changed after facts exist.

### Family integrity

* Guidance and surprise Drivers require exactly one proven metric base.

* Action Drivers have no base relationship.

* SAME_AS means identical reusable meaning.

* BASE_METRIC means related family, not identical meaning.

* Never use one relationship as the other.

* Replace the temporary suffix-only surprise-home approximation on the V2 path with actual family relationships.

* Do not alter the V1 behavior before the switch.

## Born-complete creation

A new Driver must be created with its first accepted fact as one atomic plan.

Requirements:

1. Stamp the final name and type before downstream validation.

2. Validate using an in-memory Driver carrying that final name and type.

3. If every fact for the proposed Driver fails, plan no Driver.

4. Group all accepted same-event facts for one new Driver.

5. Produce exactly one Driver-creation operation.

6. Select the first fact deterministically by original source order.

7. Place Driver creation, the first fact, required edges, and remaining same-event facts in one transaction group.

8. Recheck source, company, Driver existence, type, collision state, and required family relationships inside the eventual transaction.

9. If the Driver appeared concurrently, never create a duplicate and never
   auto-retry. The changed Driver state may trigger a later whole-event
   re-evaluation through Step 10, using only the original event's evidence.

10. A catalog card with no graph node creates lazily:

    * use the card’s frozen type and definitional evidence;
    * require an accepted first fact;
    * create no empty catalog node.

11. A live-created Driver freezes raw qualifying birth quotes, never a model-written summary.

12. A bare-name Driver cannot be born with an unknown first state.

13. A properly proven guidance or surprise Driver may begin with unknown.

14. Failure must yield zero partial writes.

Step 4 proves the plan and rollback behavior with controlled transaction doubles. Actual database transaction proof remains part of the later activation gate.

## The one reversible same-meaning link mechanism

Use one judge and two triggers:

* synchronous proposal during admission—shadow only; no link;

### Pair construction

* target name;
* target’s frozen birth evidence;
* target industry.

Never supply producer advocacy, prior verdict wording, similarity scores, or the detector’s conclusion.

### Mechanical refusals

Refuse without a model only when the frozen design directly supplies the rule:

* base, guidance, and surprise flavors differ;
* terminal suffixes conflict;
* per-unit denominators conflict;
* one name includes a different portion of the quantity;
* the target is quarantined or not eligible;
* a gated rule has not passed its experiment.

Do not add semantic word lists or named industry-pair examples. Named-series,
benchmark, cause-versus-effect, and industry-homonym questions remain model
decisions under the same object, business-scope, and mechanism test.

### Strong identity judge

Every new semantic identity decision receives this one independent review.
The reader, router, candidate search, exact spelling, and deterministic token
checks may propose or refuse; none may approve semantic identity. Company,
industry, and mention counts neither change this rule nor add a second judge.
An exact replay of an unchanged frozen decision reuses its recorded result.

All five checks must pass, with evidence from both sides:

1. same exact object—not a broader or narrower class;
2. same business population and ownership scope;
3. same causal mechanism and position;
4. no equally plausible competing Driver;
5. the target’s frozen birth evidence describes one coherent mechanism.

Any failure or uncertainty keeps the Drivers separate.

### Applying an approved link

Plan one reversible variant-to-head SAME_AS relationship carrying:

* trigger;
* exact judge identity;
* decision time;
* frozen-anchor hash;
* evidence quotes.

Code then:

* elects the head through the frozen order;
* flattens chains into a star;
* preserves each fact on its original Driver;
* never deletes or re-keys history;
* prevents variants from becoming link targets;
* records refused pairs;
* rechecks a refused pair only after an exact owner-registered evidence or
  state change affecting that pair.

### Deferred pairs

Maintain one deferred-pair record:

* no duplicate ledger;
* no Driver created around a flagged target;
* only an exact owner-registered evidence change reopens the pair;
* only the target owner's exact recovery-state change reopens affected pairs;
* aging may raise an operational alarm but never changes semantic state;
* every transition is audited;
* no scheduler is built here.

## Recovery core

For every suspected wrong link:

1. Preserve the raw evidence.
2. Temporarily quarantine the link from history-based signals.
3. Send raw evidence—not the detector’s conclusion—to two independent Sonnet 5
   high-effort reviewers.
4. Require both to confirm different meanings.
5. Use a third reviewer for seed-built links.
6. If still inconclusive, retain quarantine and raise the defect class as one owner question.
7. Confirmed error flips only the reversible quarantine state.
8. Facts remain on their original Drivers.
9. Mark an individually misattached fact disputed without changing its identity.
10. Propagate safety holds across affected variants and base-family relationships.
11. Write one immutable recovery record.
12. Add the case to regression evidence.
13. Allow later reversal through the same governed process.

Step 4 builds and tests the recovery decision and dry-run plans. It does not run a background recovery service.
